# 작업 절차

## 시작

루트 지침과 관련 분야 명세, 담당 폴더 지침을 읽는다. 한 작업에서 전체 자료를 반복해서 읽기보다 영향을 받는 REQ를 고른다.
출처 논쟁이나 이전 기능 복원 여부는 sources의 정정 표를 확인한다.
복잡한 작업은 [개발 계획](plans/implementation.md)에 진행 단위를 남긴다. 단순 수정마다 새로운 계획 파일을 만들 필요는 없다.

## 구현

제품 기능 하나의 화면→API→도메인 처리→검증이 이어지도록 만든다.
영역을 나눠 동시에 작업할 때는 파일 소유 범위와 변경할 계약을 공유한다. 다른 작업자의 수정을 되돌리지 않는다.
외부 값이 없으면 개발용 mock과 실제 연동을 분리한다. mock 사용을 기록하고 운영에서 비활성화한다.
기술 선택은 담당자가 결정하여 decisions에 이유를 남긴다. 명세 밖 기능을 편의상 끼워 넣지 않는다.

## 검증과 완료

1. 영향받은 REQ의 수용 시나리오를 확인한다.
2. 실제 서비스의 유의미한 테스트·빌드·권한 검사를 실행한다.
3. `npm run harness:check`로 문서 연결과 두 도구의 스킬 일치를 검사한다.
4. 시나리오의 구현 파일과 검증 증빙 경로를 기록한다. 아직 없는 증빙을 적지 않는다.
5. 계획에 구현/검증 결과와 다음 단계를 남긴다.

테스트를 통과했다는 사실과 요구사항이 실기기에서 충족됐다는 사실을 구분한다.
서비스가 아직 없다면 하네스가 준비됐다고만 보고한다.

## 스킬 유지보수

`.agents/skills/<name>/SKILL.md`를 수정한 뒤 `npm run harness:sync`를 실행한다.
동기화본 `.claude/skills`도 버전 관리한다. 원본 삭제 시 남은 복사본은 검사가 실패하므로 삭제 대상 확인 후 함께 정리한다.
동기화 도구는 임의 파일을 삭제하지 않는다. 새 스킬의 name/description과 상대 문서 링크를 검증한다.

## 새 세션 인계

다음 에이전트가 필요한 내용은 계획 파일에 남긴다: 완료된 단계, 실행한 명령·결과, 남은 과제, 외부 연동 상태.
채팅에만 남은 정책을 다음 세션이 알 것이라고 가정하지 않는다. 문서는 개인정보·secret 저장소가 아니다.
