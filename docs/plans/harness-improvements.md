# 하네스 개선 계획

작성: 2026-09-23. 근거: [로컬 평가와 공개 사례 비교](../reviews/harness-assessment-2026-09-23.md). 대상은 기존 Codex/Claude 공유 하네스이며 제품 기능 요구사항은 [명세](../spec/index.md)를 유지한다.

목표는 실제 도구 입력에 맞는 훅, 실행 결과에 연결된 완료 판정, 개발 전 준비 가능한 CI, 새 세션에서 재개 가능한 작업 단위를 갖추는 것이다. 아래 항목은 제안된 후속 구현이며 M0의 문서 반영만 완료했다. 하네스 개선 전체를 제품 개발의 선행 조건으로 삼지 않는다.

## 진행 상태

- [x] M0: CI 선구축 지침·DEC-013·출처 반영, 기준 검사와 결함 재현, 평가/계획 작성.
- [ ] M1: 실제 도구 입력·경로·출력에 맞게 훅 보완.
- [ ] M2: 완료 판정의 실행 증빙 구조와 검사 강화.
- [ ] M3: 앱 없이 실행 가능한 CI 검사 보강과 서비스 연결 기준 구현.
- [ ] M4: 작업 상태·실행 준비·계약 초안·인계 구조 보강.
- [ ] M5: Codex/Claude 새 세션 평가와 수정 전후 비교.

## M1 — 훅의 실제 입력·기동·출력 보완

대상: `harness/hooks.mjs`, `harness/hooks.test.mjs`, `.codex/hooks.json`, `.claude/settings.json`, 두 도구의 README. 근거: H-01/02/03/05.

1. Codex `apply_patch.tool_input.command`, Claude Write/Edit, Bash/PowerShell을 공통 입력으로 정규화한다. 도구 이름의 임의 추측 대신 공식 규약과 지원 버전을 기록한다.
2. 패치의 추가/수정/이동 대상별 경로와 추가 내용을 추출한다. 여러 파일 중 `.env`가 하나 있다고 다른 소스 파일 검사를 면제하지 않는다. 삭제된 옛 비밀 문자열과 새로 추가한 문자열도 구분한다.
3. 절대 경로를 프로젝트 루트 기준으로 정규화한다. 루트 밖·공백 포함 경로·하위 cwd·worktree를 다룬다. Codex 훅 명령은 cwd와 무관하게 해당 checkout의 스크립트를 찾게 한다.
4. Claude PowerShell matcher와 정규화 코드를 함께 갱신한다. 두 런타임의 deny 및 `additionalContext` 출력과 종료 코드를 자식 프로세스로 검사한다.
5. 잘못된 JSON/알 수 없는 입력 형식의 진단 방식을 문서화한다. 모든 셸 프로그램의 의미를 정규식만으로 차단할 수 있다고 보장하지 않는다.

완료 조건: 현재 H-01/02/03/05 재현이 수정 전에는 실패하고 수정 후에는 통과하는 테스트가 존재한다. 실제 위험 명령이나 비밀값 없이 합성 이벤트로 검사한다. 기존 정상 개발 명령·예시 환경값은 허용하며 루트/하위 cwd 모두 올바른 훅 파일을 실행한다. 현재 20개 검사와 신규 회귀 검사가 Windows·Ubuntu에서 통과해야 플랫폼 호환 완료로 기록한다.

## M2 — 파일 존재와 실행 검증 완료를 구분

대상: `harness/check.mjs`, `harness/check.test.mjs`, `tests/acceptance/README.md`, `docs/verification.md`, 필요 시 시나리오 스키마와 새 증빙 스키마. 근거: H-04/06.

기존 38개 시나리오의 `specified` 상태는 유지한다. schema 변경이 필요하면 버전을 올리고 일괄 마이그레이션을 같은 변경에 포함한다. 실행 결과에는 최소한 run ID, 시나리오 ID, 검사 명령과 cwd, 성공/실패/건너뜀, 실행 시각, 도구 버전/환경, 검사 대상 commit 또는 입력 digest, 결과물 경로가 있어야 한다.

`implementation`은 실제 대상 파일을 연결하고, `evidence`는 테스트 코드만으로 채우지 않는다. 자동 검사는 결과를 직접 생산하고 CI가 재실행해 확인한다. 카메라/학교 연동처럼 사람이 관찰해야 하는 검증은 유형·환경·관찰 결과를 명시하고 자동 단위 테스트와 구분한다. 결과물에는 얼굴·벡터·토큰·개인정보를 넣지 않는다.

완료 조건: README만 넣은 H-04 입력, 실패 결과, 건너뛴 결과, 다른 시나리오 결과, 검사 대상 코드가 바뀐 오래된 증빙이 거부된다. 올바른 합성 결과는 허용되며 초기 `specified` 카탈로그는 계속 통과한다. 증빙 JSON을 작성했다는 이유만으로 실제 제품 동작을 증명했다고 보고하지 않는다.

## M3 — CI 선구축을 실제 검사로 연결

대상: `.github/workflows/harness.yml`, 필요 시 별도 설정 검사 워크플로, `package.json`, `docs/verification.md`, 서비스 명령 등록 파일. 근거: H-06, DEC-013.

우선 기존 Windows/Ubuntu 하네스 검사를 유지하고, [actionlint](https://github.com/rhysd/actionlint)로 워크플로를, [Gitleaks](https://github.com/gitleaks/gitleaks)로 Git에 들어가는 변경을 검사하는 방안을 구현한다. 버전·배포 체크섬 또는 action commit을 고정하고 갱신 방법을 남긴다. secret 결과는 마스킹하며 합성 테스트 예외는 해당 fixture에만 제한한다. Codex TOML·두 런타임 JSON 설정은 구문뿐 아니라 필수 command/matcher 구조를 확인한다.

현재 존재하지 않는 서비스 명령을 만들어 성공 처리하지 않는다. 서비스별 준비 상태와 `cwd/test/build`를 한 곳에서 관리하고, 실행 가능한 골격을 추가하는 변경에서 명령을 등록한다. 외부 의존성 설치를 추가하면 기존 무설치 하네스 검사와 별도 검사 명령을 명확히 구분한다.

| 서비스/배포 상태 | CI 행동 | 결과 해석 |
| --- | --- | --- |
| 아직 서비스가 없음 | 하네스·설정 검사를 실행; 서비스 작업은 미준비 표시 | 서비스 검증 수에 포함하지 않음 |
| 골격·명령 준비 | 테스트·빌드를 실제 실행 | 실제 통과한 범위만 기록 |
| 활성 서비스에서 명령/필수 파일 누락 | 실패 | 존재 조건에 따른 조용한 건너뜀 금지 |
| 배포 대상/산출물 미준비 | 배포 설정 검사만 실행 | 배포 성공 아님 |
| 배포 산출물·환경·요청 범위 준비 | 해당 환경에서 배포 후 health/readiness 검증 | 배포 대상·산출물 버전·결과 기록 |

조건부 건너뜀이 required check에서 성공으로 보일 수 있으므로 서비스 상태를 종합하는 검사가 실행 여부까지 확인해야 한다. [GitHub 동작 근거](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-jobs-with-conditions)

완료 조건: 앱이 없는 checkout에서도 실질적인 설정/하네스 검사가 돈다. 잘못된 워크플로, 합성 secret, 잘못된 훅 설정, 활성 서비스 명령 누락을 주입한 격리 fixture에서 실패를 관찰한다. 정상 PR은 Ubuntu/Windows 원격 run URL·대상 SHA와 함께 증빙한다. 원격 실행이 없으면 로컬 검증 완료까지만 표시한다.

## M4 — 작업 재개와 독립 개발 경로 정리

대상: `docs/workflow.md`, `docs/plans/implementation.md`, 해당 API 계획, `contracts/README.md`, `docs/architecture.md`, 관련 구현 스킬. 근거: H-07.

각 기능 계획의 최상단 또는 하나의 공통 작업 목록에 최소 레코드를 둔다: 작업 ID, 연결 REQ/ACC, 담당·편집 파일, 선행 작업, `ready/in_progress/blocked/done`, 차단 이유, 최근 검사 증빙, 다음 실행 명령. 여러 곳에 별도 진척 원장을 복제하지 않는다. 완료는 M2의 증빙 규칙과 연결한다.

`API명세서/API명세서`는 현재 접근 가능한 위치·출처를 확인한다. 확인할 수 없으면 외부 자료 미확인으로 표시하고 기존 계획을 계약 초안으로 다룬다. 내부 계약은 공급자/소비자가 검토하는 비어 있지 않은 초안을 구현 전에도 작성할 수 있게 한다. 제공되지 않은 DataGSM 필드/이벤트를 확정 계약으로 만들지 않는다.

인증/학교 연동이 필요한 통합과 외부 접근 없이 가능한 출석 도메인·QR 계약·UI·설정 검사 작업을 구분한다. 기존 "인증과 동기화가 먼저" 문장을 실제 의존성으로 바꾼다. health·UI·계약·도메인 테스트마다 필요하지 않은 외부 확인을 공통 차단 조건으로 두지 않는다.

새 세션에서는 저장소 상태와 작업 레코드, 사용 가능한 runtime/명령, baseline 검사를 확인한 뒤 다음 ready 작업을 고른다. 환경 점검 스크립트를 추가한다면 읽기 전용이고 반복 실행 가능하게 하며, 없는 서비스는 미준비로 표시하고 자동 설치·서버 실행으로 숨기지 않는다.

완료 조건: 대화 기록 없이 다음 작업 하나와 실제 가능한 명령을 고를 수 있다. 외부 연동이 막힌 fixture에서도 무관한 작업은 ready로 남는다. 명세 변경·읽기 전용 질의·작은 수정마다 전체 자료 읽기나 전체 계획 재작성을 강제하지 않는다. 스킬을 수정했다면 `npm run harness:sync` 후 검사한다.

## M5 — 실제 에이전트 동작을 측정

대상: 향후 `tests/agent-evals/`의 합성 과제·채점 기준과 결과 요약, 두 도구의 사용 안내. 지금은 생성하거나 실행하지 않았다. 근거: H-08.

첫 평가는 아래 6개 과제를 격리 checkout에서 도구별 새 세션으로 실행한다. 파일·검사 결과를 우선 채점하고, 모델의 완료 문장만으로 통과시키지 않는다.

| 과제 | 관찰할 결과 |
| --- | --- |
| 읽기 전용 상태 질문 | 근거 있는 답변, 파일 변경 없음 |
| 작은 하네스 수정 | 관련 지침 선택, 제한된 diff, 필요한 검사 실행 |
| 합성 제품 정책 변경 | REQ·출처·시나리오·계획 연결, 폐기 정책 부활 없음 |
| 검증 실패가 있는 작업 재개 | 실패를 성공으로 보고하지 않음, 원인과 다음 작업 유지 |
| 세션 종료 후 이어하기 | 작업 기록에서 재개, 기존 변경 보존, 완료 단계 불필요 반복 없음 |
| 외부 API 미확인 | 없는 필드 발명 없음, 미확인 연동 구분, 독립 작업 진행 |

처음에는 각 과제 1회로 실행 경로를 확인하고, 수정 전후 비교에는 도구별·과제별 3회를 초기 표본으로 제안한다. 작은 표본은 광범위한 성능 우위를 증명하지 않는다. 동일 fixture·과제·환경과 해당 도구 내 동일 모델/설정을 유지하고 도구/모델 버전, 성공/실패/미실행, 소요 시간, 사용자 개입 횟수, 측정 가능한 사용량을 남긴다. 원시 비밀값과 불필요한 전체 대화는 증빙에 보관하지 않는다.

완료 조건: 두 도구 모두 새 세션에서 공통 지침/스킬을 사용하고 핵심 성공 기준을 충족한 증거가 있다. 미지원 클라이언트·OS·버전은 별도로 명시한다. 추가 평가자·자동 반복·Stop 훅은 이 결과로 이득이 확인되는 경우에만 후속 검토한다. 공개 데모의 자동 커밋/무한 루프를 기본값으로 도입하지 않는다.

## 검증과 인계

현재 존재하는 명령은 루트의 `npm run harness:check`다. 스킬 원본을 바꾼 경우에만 `npm run harness:sync`를 먼저 실행한다. 새 검사 명령은 실제 구현한 변경에서 `package.json`과 검증 기준에 등록하고 예상 실패/성공 사례도 함께 남긴다.

각 마일스톤 종료 시 이 문서의 체크 상태, 실제 실행 명령·환경·결과, 미검증 사항, 다음 작업을 갱신한다. 첫 구현 작업은 M1의 공식 Codex 패치 입력과 Claude PowerShell 입력 회귀 검사 추가다. 세부 CI 구축과 제품 개발은 준비된 독립 작업부터 병행할 수 있다.
